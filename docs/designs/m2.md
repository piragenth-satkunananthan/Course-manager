M2 covers four groups from `CONTEXT.md`: **Attendance**, **Timetable accuracy** (Break Weeks, Holidays, Session Groups, every-2-weeks classes), **Notes and files** (Notes, Attachments, search) and **Setup and extras** (setup wizard, dark mode, Calendar Feed, Export my data). ## Decisions for the product owner

Each has a recommendation. A decision marked ⚠ changes an approved requirement in `CONTEXT.md` or the approved design if you take the recommendation; those wording changes go in one docs-only PR before any M2 code. D10 creates Azure infrastructure: even once decided, it is created only with a separate go-ahead.

### Attendance

**D1. ⚠ When does a Course turn red, and what does "you can miss N more" count?**

- Whole Semester: N counts the classes still to come and assumes you attend them all. Red only when you can no longer reach the minimum, even attending every class left. Early on, the rate can be below the minimum with no warning (for example "0% · min 80% · You can miss 11 more" after one absence in week 1).
- So far only: N counts only classes already marked. Red as soon as the rate so far is below the minimum. This is CONTEXT's literal wording. One absence in the first week turns the Course red and shows "you can miss 0 more".

*Recommended:* Whole Semester. The so-far version goes red after a single early absence, so the Student learns to ignore it. The minimum is always shown beside the rate, so a low early rate is still visible. This changes CONTEXT's sentence "turns red … when the rate falls below the minimum" to "turns red … when the minimum can no longer be reached". That needs your OK, and ticket 2 updates CONTEXT.md.

*Decision (2026-11-24):* the recommended option, recorded as U21.

**D2. When Attendance ships mid-semester, every past class shows as "to mark". How should the Student catch up?**

- Do nothing: the Student marks each class one by one.
- Add one "Mark all shown as Present" button on the To mark list, with a confirm. It respects the Course filter, and every mark can still be changed. The Student marks the few absences first, then the rest in one go.
- Count only the last 14 days in the counter. Older unmarked classes stay under "All" but stop nagging.

*Recommended:* The "Mark all shown as Present" button. It matches how people remember attendance ("I missed two, I was at the rest") and keeps the counter honest. It is its own small last ticket, so it can be dropped.

*Decision (2026-11-24):* the recommended option, recorded as U22.

**D3. ⚠ The approved dashboard order is fixed (design-system §7.1: Overdue → Today → Due soon → TBA Exams → Check these → Recent changes). Where does the new Attendance section go?**

- After Today: Overdue → Today → Attendance → Due soon → … On desktop, in the left column under Today.
- After Due soon, so all Deadlines come first.
- At the very end, after Recent changes.

*Recommended:* After Today. Marking happens on today's classes, and the section shows only when a Course is red or classes are waiting to be marked. Overdue still comes first.

*Decision (2026-11-24):* the recommended option, recorded as U23.

**D4. Do extra sessions (one-off classes added by you or the AI) count toward the rate?**

- Yes, like any lecture, tutorial or lab. The table gets a second key (session_change_id), a check and a second unique index.
- No, only weekly classes count. The table keeps the shape reserved in design §3, with no session_change_id, check or second index.

*Recommended:* Yes. They are real classes, and lecturers usually take attendance at make-up classes. CONTEXT says each "Class Session occurrence" is marked, which does not settle it, so it needs your call.

*Decision (2026-11-24):* the recommended option, recorded as U24.

### Timetable accuracy

**D5. Do Break Weeks count when numbering weeks? This decides what "week 5" and "every 2 weeks" mean after a break.**

- Skip Break Weeks: the week after a 1-week break carries on the count (week 7, not week 8), and every-2-weeks classes keep their rhythm
- Count every calendar week from the Semester start, breaks included

*Recommended:* Skip Break Weeks. Universities number teaching weeks, and lab rotations usually carry on after a break. Counting calendar weeks would put every-2-weeks labs in the wrong weeks after a break. If your university numbers weeks differently, say so and the rule changes in one function.

*Decision (2026-11-24):* the recommended option, recorded as U25.

**D6. ⚠ A message is for another Session Group that exists on that Course ("Group A lab moved to 3pm", "Group A report due 27th"). What should happen? Note: options 1 and 2 change an approved rule in CONTEXT.md (line 76: "Messages that look like a deadline but caused no change are flagged Possibly missed"). Option 3 keeps it.**

- Ignore it quietly: no change, not in Possibly Missed, not in the digest. CONTEXT.md line 76 gets an exception for other Session Groups.
- Ignore class changes quietly, but still flag messages that look like a deadline (due, exam, quiz) as Possibly Missed. CONTEXT.md line 76 is reworded to match.
- Flag it as Possibly Missed if it looks like a deadline, under the current rule. No CONTEXT.md change.

*Recommended:* Option 1. Other groups' notices would fill Possibly Missed, and a list that is mostly noise teaches you to skip it, which is how real deadlines get missed. The safety nets: the AI only says "another group" when the name matches a group you set up, an unknown name still goes to Possibly Missed, and the eval must pass 100% of deadline cases twice. Pick option 2 if you want a second look at other groups' deadlines.

*Decision (2026-11-24):* the recommended option, recorded as U26.

**D7. How should Session Groups be stored? The approved design (U8, §3) already reserves a session_group table.**

- A session_group table, as planned: you add groups to a Course, then tie classes to them and pick yours
- Plain text labels: each class has a group label ("Group B"), the Course stores your label, and the Course's groups are the distinct labels on its classes

*Recommended:* Keep the table. It is already in the approved design, so nothing changes there. A typo can't silently create a second group. You can pick a group before you enter its classes. And the AI gets a clean list of names, which the "does this group exist" check needs. Text labels would save one table, 3 endpoints and the chip editor, but they need a design change and are easier to get wrong.

*Decision (2026-11-24):* the recommended option, recorded as U27.

### Notes and files

**D8. Which kind of editor should Notes use?**

- A: A what-you-see editor (Tiptap). Bold looks bold as you type, and there is a toolbar. The Note is stored as structured data that the server checks
- B: Markdown. You type ## for headings and ** for bold (the toolbar adds these), with a preview tab. Simpler and easy to export as text, but you see the symbols while writing

*Recommended:* A. The brief asks for a formatted-text editor, and the design-system screen already shows a toolbar. You test it on your phone in ticket 1. If it misbehaves with your keyboard, we switch to B before ticket 1 closes.

*Decision (2026-11-24):* the recommended option, recorded as U28.

**D9. ⚠ How should Notes save? (Option A is an exception to the approved rule U7, so it needs your approval.)**

- A: Autosave 1.5 s after you stop typing. If another device changed the same Note, a banner offers 'Keep mine' or 'Load the other version'. This replaces U7's 'reload and show a toast' for Notes only, because a reload would throw away the text you just typed
- B: A Save button, like the other forms, following U7 as it is (on a conflict, the Note reloads and you type your change again), with a warning if you leave with unsaved changes

*Recommended:* A. Notes are often typed on a phone in class, and a closed tab should not lose text. Nothing is overwritten unless you choose it. U7 stays as it is for every other item.

*Decision (2026-11-24):* the recommended option, recorded as U29.

**D10. Where should Attachments be stored? (This is an infrastructure change, so it needs your approval before the account is created.)**

- A: A new storage account used only for Attachments
- B: A new container in the existing backup storage account

*Recommended:* A. It costs nothing extra. It keeps the web app's storage key away from the backups, so a leaked key could not delete them.

*Decision (2026-11-24):* the recommended option, recorded as U30.

**D11. Which kinds of file can be attached? The Notes requirement says 'mainly PDFs, max 20 MB'.**

- A: PDF and Office files (Word, Excel, PowerPoint) only
- B: A, plus photos (.png, .jpg), for example a photo of the whiteboard
- C: B, plus .zip files (for example lab code)

*Recommended:* B. Photos of the board are a common need on a phone, and they add only two rows to the allow-list. Zip files can hold anything and are rarely study material, so leave them out for v1.

*Decision (2026-11-24):* the recommended option, recorded as U31.

**D12. ⚠ How should Attachments be protected against loss? (The nightly backup covers only the database.) Options A and B change the approved line in CONTEXT.md from 'Backups age out within 7 days' to 'Backups and deleted Attachments are erased within 7 days', and the account dialog and email say the same.**

- A: Azure's built-in 3 copies (LRS), plus 'soft delete' for 7 days (a deleted Attachment can be recovered for a week)
- B: A, plus you download the Attachments with the monthly backup download (an az CLI step in the runbook, encrypted with the same age key as the backups)
- C: No soft delete. Deleted Attachments are gone at once, and the CONTEXT.md line stays as it is

*Recommended:* B. Soft delete covers mistakes. The monthly download covers losing the Azure account, which is the same risk already accepted for the database backups (U9). No app code is needed.

*Decision (2026-11-24):* the recommended option, recorded as U32.

**D13. Which Semesters should Search cover?**

- A: Every Semester. Results from older Semesters show the Semester's name
- B: Only the current Semester

*Recommended:* A. Searching older Semesters helps when you revise earlier material. The label keeps it clear which Semester a result belongs to.

*Decision (2026-11-24):* the recommended option, recorded as U33.

### Setup and extras

**D14. ⚠ Should the setup wizard have a step for the Deadlines that are already open? CONTEXT.md says "At setup, the Student types in the Deadlines that are already open", because messages from before linking are never read. But the wizard line in CONTEXT.md lists only 4 steps.**

- Add it as step 4 (Semester, Courses, Classes, Open Deadlines, WhatsApp)
- Keep 4 steps; the dashboard's empty state already asks for Deadlines

*Recommended:* Add it as step 4, before WhatsApp. It reuses the existing Add Assignment and Add Exam forms. Typing them in before linking groups means a repeated announcement updates the item you typed instead of making a second one.

*Decision (2026-11-24):* the recommended option, recorded as U34.

**D15. Your account is already set up, so the wizard will never open on its own for you. Should you also be able to start it when a new Semester begins?**

- First sign-in only (as CONTEXT.md says now)
- Also from Settings → Semesters: "Set up a new Semester" runs the same steps for the new Semester

*Recommended:* Also from Settings. It is one button that sets the wizard back to step 1, and a new Semester is when you would actually use it. The wizard reminds you to set the new Semester as current, and to archive the old one after its exams.

*Decision (2026-11-24):* the recommended option, recorded as U35.

**D16. How should dark mode be chosen?**

- Follow the device's light or dark setting only, with no switch
- Follow the device by default, plus a System, Light or Dark switch in Settings, saved on each device in a cookie
- A Light or Dark choice saved to your account, the same on every device

*Recommended:* Follow the device only. It is pure CSS, with no cookie, no Settings section and no extra test, and it does what CONTEXT.md asks ("Light and dark mode"). If you later want to force Light or Dark on one device, the switch is a small follow-up ticket, and its design is already written above.

*Decision (2026-11-24):* the recommended option, recorded as U36.

**D17. Can Settings show the calendar link again later, or only once?**

- Only once, right after it's created or reset; only a hash is stored
- Any time; the link is stored encrypted with the existing data key

*Recommended:* Only once. A leaked database or backup then can't give the link away. If you lose it, Reset makes a new one in one tap. You add it to your calendar app only once, so this costs little.

*Decision (2026-11-24):* the recommended option, recorded as U37.

**D18. ⚠ CONTEXT.md says "Export my data" downloads "everything". What should "everything" mean?**

- What you made or can see: Semesters, Courses, Nicknames, classes, Session Changes, Assignments, Exams, linked groups and the Activity Log (plus Notes, Attendance and files when they exist)
- Every table that holds your data, including internal records such as stored WhatsApp message details, AI batches, the email log and version history (still without passwords or WhatsApp keys)

*Recommended:* What you made or can see. The internal records mean nothing outside the app, and the WhatsApp message rows hold classmates' words and names, which D1 says are erased when the Semester is archived. The smaller export is also much simpler and safer to build: a few MB, built in one go, with no streaming. CONTEXT.md would be updated to say exactly what is left out.

*Decision (2026-11-24):* the recommended option, recorded as U38.

## Where the groups meet

What the cross-group check found, and how this design resolves it. These resolutions apply over the group sections below.

Rebase each branch and generate its migration again just before it merges. - **Attendance, Timetable accuracy.** Attendance counts whatever getOccurrences returns. If it ships before Break Weeks, Holidays and every-2-weeks, Break Week classes show as "to mark" and inflate F, so "you can miss N more" is too high. Attendance's stop-gap advice ("cancel them by hand in the meantime") also stops working once 1a ships, because 1a rejects a manual cancel on an off-day and hides older cancels there.
  **Resolution:** Build Timetable 1a, 2 and 3a before any Attendance ticket, as both groups recommend. Then remove the "cancel them by hand" stop-gap from the Attendance design. No code change is needed in Attendance, because it already reads only through getOccurrences.
- **Attendance, Timetable accuracy.** Session Groups with no group picked. The Timetable rule shows every group's classes until the Student picks one. Attendance then counts both Group A's and Group B's labs: the other group's past labs show as "to mark", and its future labs inflate F, so N is too high. This is the unsafe direction for a 'can I skip?' number.
  **Resolution:** Keep the Timetable rule. On the Attendance page and the Course attendance line, show one line when a Course has Session Groups but none is picked: "Pick your Session Group on the Course page so only your classes count." Add this to the acceptance criteria of the Attendance page ticket. The data is already in the Course DTO (sessionGroups, mySessionGroupId).
- **Attendance, Timetable accuracy.** Some timetable edits quietly stop marks counting: switching your Session Group, changing a class to every 2 weeks, and moving the Semester start date (which renumbers the Teaching Weeks). The marks are kept but no longer count. The edit forms don't say so, so the rate can drop with no warning.
  **Resolution:** Accept the 'kept, not deleted' rule. Add one helper line in two places: the "Your Session Group" select and the Semester start date helper ("…renumbers the Teaching Weeks. Attendance marks on classes that move stop counting until they move back."). Whichever of Attendance ticket 2 and Timetable 2/3a ships second adds the words. ## Attendance

### Overview

The university sets a minimum Attendance to sit a Course's exams. This feature lets the Student mark each class that has started as Present, Absent or Excused, with one tap. Each Course then shows its rate, its minimum, and how many more classes the Student can miss ("you can miss N more").

The design adds very little. One small table stores the marks. One new column stores each Course's minimum. Everything else is **worked out when a page loads** from the Occurrences the app already builds (`expandOccurrences`): the rate, N and the unmarked count. Nothing is stored that could go out of date. When Break Weeks, Holidays, Session Groups, every-2-weeks classes or AI Session Changes change the timetable, the numbers follow on the next page load.

The AI never reads or writes Attendance. A message like "attendance will be taken today" stays ignored chatter (the existing `chatter-attendance` test case).

### User stories

1. When a class has started, I tap **Present**, **Absent** or **Excused** on it, on the dashboard or in the timetable day list. One tap saves it.
2. I tap the chosen mark again to clear it. I tap another mark to change it.
3. Each Course shows "86% · min 80% · You can miss 4 more". The line turns amber when N is 2 or less. It turns red when I can no longer reach the minimum.
4. A red Course also shows a warning on the dashboard.
5. The dashboard says "6 classes to mark". It links to a list where I catch up.
6. I set a Course's minimum (default 80%) in the Course form.
7. A cancelled class has no buttons and never counts. If the AI cancels a class I had already marked, that mark stops counting. If the cancel is undone, the mark counts again.

### Domain rules

**The key of a mark.** One rule, in one helper `attendanceKey(o)` in `src/lib/occurrence-key.ts`, next to `occurrenceKey`. The buttons and the server both use it:
- If `classSessionId` is set (a weekly class, including a rescheduled or cancelled one): the key is `(classSessionId, originalDate ?? date)`. So a rescheduled class keeps its mark when it moves.
- Otherwise (an extra session): the key is `sessionChangeId`. Extra sessions count like any lecture, tutorial or lab (decision A4).

A rescheduled or cancelled weekly class also carries a `sessionChangeId` in the Occurrence DTO. That id is **never** used as an attendance key. The server refuses a `sessionChangeId` whose change is a cancel or a reschedule. (The existing `occurrenceKey` is a list key, not this key, because it includes the shown date.)

**When a class can be marked.** A pure `canMark(o, now)` sits next to `isHappeningNow` in `src/server/domain/occurrences.ts`: the class is not cancelled, and `localToInstant(o.date, o.startTime) <= now`. For a rescheduled class this is the **new** date and time. The PUT handler and `SessionItem` both use it. A page opened before a class starts shows the buttons after its next load. That is fine, because pages reload after every write and when opened.

**Archived Courses and Semesters are read-only for Attendance.** No screen lists their classes (`getOccurrences` skips them), so PUT returns `NOT_FOUND` for them too.

**Each Occurrence counts once.** For every Occurrence in the Course's Semester that is not cancelled:
- If it has started, it counts by its mark: Present, Absent, Excused or unmarked.
- If it hasn't started, it goes in F (the classes still to come). Any mark on it is **ignored** until it starts. This happens when a marked class is later moved to a future date, or an extra session's date is moved later. The mark is kept and counts again once the class starts.

**Marks that no longer match an Occurrence are kept, not deleted.** They just don't count. This covers:
- an AI or manual cancel after marking (undoing the cancel brings the mark back);
- a day later added as a Holiday or inside a Break Week (Timetable accuracy group);
- a Session Group change, or a weekly class whose day was edited (the old days' Occurrences disappear);
- a deleted extra session (it is soft-deleted, so its mark stays but doesn't count);
- the Semester getting shorter: the Student edits the end date, or undoes an AI Semester extension (U16). Marks in the removed weeks come back if the weeks return.

Deleting a weekly Class Session, an extra session's row, or a Course deletes the marks with it (cascade). The delete dialogs say so.

**The numbers, per Course** (a pure function `attendanceSummary` in `src/server/domain/attendance.ts`):
- `P` = counted Present marks. `A` = counted Absent marks. Excused and unmarked classes don't count.
- **Rate** = `P / (P + A)`, shown as a whole percent, rounded down. With no counted marks it shows "No marks yet". The minimum is always shown beside the rate ("86% · min 80%"), so a low rate early in the Semester isn't confusing.
- **Unmarked** = classes that have started, are not cancelled, and have no mark.
- **"You can miss N more"** (decision A1, recommended version): `F` = classes in the Semester that haven't started and aren't cancelled. `T = P + A + F`. `N = floor(T × (100 − min) / 100) − A`, in whole numbers only. This assumes the Student attends every class left.
- **Unmarked past classes are left out of T.** So N is a little lower until they are marked. This is the safe direction. It is why marking an old class Present can raise N by one.
- **State:** `ok` when N ≥ 3, `amber` when N is 0, 1 or 2, `red` when N < 0 (the minimum can no longer be reached). With T = 0 the state is `none`.
- Lectures, Tutorials and Labs count equally. A Practical Course is its own Course, with its own minimum and its own rate.

### Data model changes (migrations `0011` and `0012`)

| Table | Change |
|---|---|
| `attendance` (new; reserved in §3) | `id`, `student_id` (cascade), `class_session_id` (nullable, cascade), `occurrence_date date` (nullable), `session_change_id` (nullable, cascade), `status` enum `attendance_status` (`present`, `absent`, `excused`), `created_at`, `updated_at`. Check: either (`class_session_id` and `occurrence_date`) or `session_change_id`, never both. Unique `(class_session_id, occurrence_date)` where `class_session_id` is not null. There is no `course_id` column. A mark already reaches its Course through its Class Session or Session Change, and both of those cascade when a Course is deleted. With about 300 marks a Semester, the app reads the Student's marks by `student_id` and matches them to Occurrences in memory. Each Occurrence already carries its `courseId`.

The Student owns `attendance`. It has no `version`, no `field_set_at` and no `entity_version` rows, because the AI can't change it. A later tap simply replaces the mark (upsert), like Assignment status. Deleting the Student removes the marks (cascade). Archiving changes nothing.

**PUT errors**, checked in this order (same style as `createSessionChange` in `src/server/data/timetable.ts`):
1. The Class Session or Session Change isn't the Student's, or its Course or Semester is archived: `NOT_FOUND` ("Class").
2. The `sessionChangeId` is a cancel or a reschedule, not an extra: `VALIDATION`, field `sessionChangeId`, "Mark the weekly class instead".
3. The date isn't one of the class's Occurrences: `VALIDATION`, field `date`, reusing the `NOT_A_CLASS_DAY` message.
4. The class is cancelled: `VALIDATION`, "A cancelled class can't be marked".
5. It hasn't started (`canMark` is false): `VALIDATION`, "This class hasn't started yet".

The handler finds the Occurrence by calling the existing `getOccurrences(studentId, semesterStart, today)` and matching `attendanceKey`. It doesn't trust the browser's word that the class exists. Data code lives in a new `src/server/data/attendance.ts`, scoped by `studentId` like every other data file.

**DTO changes:**
- `Occurrence` gains `attendance: "present" | "absent" | "excused" | null`. `getOccurrences` adds it with one extra query (the Student's marks), matched by `attendanceKey`. So the dashboard, day list, week grid and month view all get it with no other changes.
- `Course` gains `attendanceMinPercent`.
- New `AttendanceSummary`: `courseId, courseCode, colour, minPercent, present, absent, unmarked, ratePercent (null when nothing counts), canMiss (N, null when T = 0), state ("none" | "ok" | "amber" | "red")`.
- `Dashboard` gains `attendance: { unmarked: number, red: AttendanceSummary[] }`.

## Timetable accuracy

### Overview

Today every Class Session repeats every week, for the whole Semester, for everyone. Real timetables are not like that. There are Break Weeks and Holidays (Poya days) with no classes. ### User stories

1. As the Student, I add the mid-semester Break Week and the Poya days to my Semester once. No classes show on those days.
2. As the Student, I open a Holiday in the day list and see "Medin Poya (Holiday). No classes." instead of an empty day.
3. As the Student, I set a lab to "every 2 weeks, from week 2". It shows only in weeks 2, 4, 6 and so on.
4. As the Student, I set a tutorial to "starts in week 3". Weeks 1 and 2 have no tutorial.
5. As the Student, I add "Group A" and "Group B" to a Course, tie each lab to its group, and pick "Group B" as mine. I then see only Group B's lab plus the classes for everyone.
6. As the Student, when the class rep posts "Group B lab cancelled" and I am in Group B, my lab is cancelled automatically, with Undo.
7. As the Student, when someone posts "Group A lab moved to 3pm", nothing changes (what happens to the message depends on decision 2).

### Domain rules

### Teaching Week (new glossary term)

**Teaching Week**: a Monday-to-Sunday week of a Semester that is not a Break Week, numbered from 1. Week 1 is the first week of the Semester that is not a Break Week. A week counts as part of the Semester if any of its days is inside the Semester's dates. Break Weeks have no number, so the week after a break carries on the count (decision 1). Holidays do not change the numbering. When a Semester is extended, the new weeks carry on the count.

Changing the Semester's start date renumbers the Teaching Weeks. So every class that is every 2 weeks or starts in week N moves with it. The Semester edit form says so (see Screens).

### Break Weeks and Holidays

- A **Break Week** is always a whole Monday-to-Sunday week. It is stored by its Monday. A 2-week break is two Break Weeks. A shorter break is entered as Holidays. (GLOSSARY.md is updated to say this.)
- A **Holiday** is one date.
- Both belong to one Semester. A Break Week must overlap the Semester. A Holiday must be inside it.
- A Holiday inside an existing Break Week is rejected: "That day is already in a Break Week". Adding a Break Week over existing Holidays is allowed. It does no harm, because the check is "is it a Holiday OR in a Break Week".
- Each has an optional name ("Medin Poya", "Mid-semester break"). With no name, the app shows "Holiday" or "Break Week".
- If the Semester's dates change later, off-days outside the new dates stay stored but do nothing. The list shows them with an "Outside the Semester" label.

### When is a date an Occurrence of a weekly Class Session

A date `d` is an Occurrence of Class Session `s` when all of these are true:

1. `d` is inside the Semester (as today).
2. `weekdayOf(d)` is `s.weekday` (as today).
3. `d` is not a Holiday.
4. `d`'s week is not a Break Week, so it has a Teaching Week number `w`.
5. `w >= s.startsWeek`.
6. `(w - s.startsWeek) % s.repeatEveryWeeks === 0`.

Rules 1-6 live in one pure function, `isOccurrenceDate(session, date, calendar)`, in `occurrences.ts`. Two places use it: `expandOccurrences`, and the manual Session Change check in `createSessionChange`. Today that check (timetable.ts line 123) only looks at the weekday and the Semester dates.

`calendar` is built once per Semester: `{ start, end, holidays: Set<date>, teachingWeekOf: Map<monday, number | null> }`. A Semester has about 20 weeks, so this is tiny.

**Rule 7, the Session Group filter**: a class is loaded only if it has no Session Group, or its Course has no group picked, or its group is the Student's group for that Course. This is a filter on which Class Sessions are loaded, not a date rule. It is applied once, in the shared loader below.

### One shared loader

The new `loadTimetable(dbOrTx, studentId, courses)` in `src/server/data/timetable.ts` returns `{ sessions, changes, calendars }`. The sessions are already filtered by group. It runs the session, change, off-day and group-pick queries in one `Promise.all`. Both `getOccurrences` and `pgAdapter.getOccurrences` call it, then call `expandOccurrences`. Any later feature that needs Occurrences (Attendance, the Calendar Feed) must read through `getOccurrences` or `loadTimetable`. It must never call `expandOccurrences` on raw table rows, because that would skip the group filter.

### Session Changes on these dates

The Session Change rules stay the same. Only the edge cases are new:

- **A cancel whose date is no longer an Occurrence is hidden, not deleted.** That happens when a Holiday is added later, the class changes to every 2 weeks, or the Student switches group. The current code already works this way. If the rule changes back, the cancel shows again. Undo still works.
- **A reschedule keeps showing on its new date** as long as its original date is inside the Semester and on the class's weekday (today's M1 check). It does not depend on off-days or repeat rules. Example: the rep posts "Monday's lecture moved to Wednesday 2pm" because Monday is Poya. Later the Student adds that Monday as a Holiday. The Wednesday class must not disappear. An announced class beats the general rule. (Other groups' reschedules are still hidden, because their Class Session is not loaded at all.)
- **A reschedule onto an off-day, and an extra session on an off-day, are shown.**
- **A manual cancel or reschedule** must name a real Occurrence date (rules 1-6). Otherwise it fails with the existing error, "That isn't a day this class meets in its Semester". The new date of a reschedule, and the date of an extra session, may be an off-day.

### Session Groups

- Session Groups are set per Course. The Student picks at most one per Course (CONTEXT.md line 26, GLOSSARY.md). This is fixed, not an open question.
- A Session Group's name is unique within its Course, ignoring case.
- A Class Session is either for everyone (no group) or tied to one group of its own Course.
- The Student's group for a Course is stored on the Course. It must be one of that Course's groups.
- **No group picked yet**: every class shows, from all groups. Hiding a class you might need is worse than seeing a few extra. This is easy to change later.
- A Practical Course has its own groups, like any Course.
- Deleting a group that still has classes is blocked: "Group B has 2 classes. Change or delete them first." Deleting the Student's own group clears their pick.
- Extra sessions have no group. An extra the AI adds is only ever for the Student's group. If the Student switches group later, old extras stay (see Risks).

### Every 2 weeks and start in week N

- `repeatEveryWeeks` is 1 or 2. `startsWeek` is 1 to 30. Both default to 1, so every existing class works exactly as before.
- "Every 2 weeks from week 1" means weeks 1, 3, 5. "From week 2" means weeks 2, 4, 6. Break Weeks have no number, so the pattern carries on after a break without flipping (decision 1).

## Notes and files


### Overview

This group adds three things:

1. **Notes.** Each Course can have any number of Notes. A Note has a title and formatted text: headings, lists, bold, links and code blocks.
2. **Attachments.** Files up to 20 MB each are attached to a Note. Decision 4 sets which kinds of file are allowed. Files are kept in a private Azure Blob container (ADR-0001). The browser sends a file **straight to Blob storage**. It opens a file **through a link that expires after 5 minutes**. Files never pass through the web container, so the 1 GB memory budget does not change.
3. **Search.** One page finds Courses, Assignments and Exams by title, and Notes by title and text. It does not look inside files (out of scope for v1).

This group does not touch the worker, the AI, the Daily Digest or Final Reminders. No new container runs in production. The only new cloud resource is one storage account for Attachments (decision 3).

M3 (saving files posted in WhatsApp groups) builds on this. It is **not designed here**. This design only avoids blocking it (see "Room for M3").

### User stories

- As the Student, I open a Course and see its Notes, most recently edited first.
- I add a Note with a title. Then I write in it with headings, lists, bold, links and code blocks. It saves as I type, so a closed tab does not lose my work.
- If I edited the same Note on another device, I'm told. I choose which version to keep. Nothing is lost without me knowing.
- I attach a lecture PDF to a Note and see a progress bar. A file that is too big, or of a kind that isn't allowed, is refused with a clear message.
- I tap an Attachment and it opens. A PDF opens in the browser. Other kinds download.
- I delete an Attachment, or a whole Note, after a confirmation.
- I type "trees" in Search. I find the Note "Week 5 – Trees", any Note whose text mentions trees, and any Assignment or Exam with that word in its title.
- When I delete a Course or my account, its Attachments are erased too.

### Data model changes

There are **two expand-only migrations**, one in each ticket. "Expand-only" means they only add things, so the previous app version still runs against the new database (§14). These are the `note` and `attachment` tables that §3 reserved for M2.

- `0011_notes.sql` (ticket 1)
- `0012_attachments.sql` (ticket 3)

**`note`** (0011)

| Column | Type | Rule |
|---|---|---|
| `id` | uuid | primary key |
| `student_id` | text | FK `user`, cascade |
| `course_id` | uuid | FK `course`, **cascade** |
| `title` | text | required, trimmed, 1–200 characters |
| `body` | jsonb | the editor's document (Tiptap JSON). Default: an empty document |
| `body_text` | text | the plain text of `body`, worked out **by the server** on every save. Search reads this. Default `''` |
| `version` | int | default 1, +1 on every save. Used for the "changed on another device" check |

The AI never writes Notes. So there is no `field_set_at` and no `entity_version` history. `version` only stops two devices from silently overwriting each other.

**`attachment`** (0012)

| Column | Type | Rule |
|---|---|---|
| `id` | uuid | primary key |
| `student_id` | text | FK `user`, cascade |

**Every blob has a row.** The `uploading` row is written **before** an upload link exists. So the `attachment` table always lists every file we could have stored, including half-finished uploads. Deleting a Note, a Course or the account deletes the blobs named in these rows, in **every status**, and then the rows. We never need to list Blob storage.

- `attachment.source`
- `attachment.content_sha256`, to skip files with the same contents
- `attachment.inbox_message_id`

The file checks and `blob.ts` are shared code, so the worker can reuse them. **M3 must decide how the worker gets access to storage.** It could get the same account key, or its own signed link that only works for the `attachments` container. Giving it the same key would put a key that can write and delete files in a second container, which weakens the reason for decision 3. `activity_event.file_too_large` already exists.

### Domain rules

**Notes**

- A Note belongs to exactly one Course. Notes on an archived Course stay readable **and editable**, because Archived means "leaves the dashboard", not "locked".
- **Editor and allowed formats (decision 1).** The editor is Tiptap with StarterKit. Headings are limited to levels 2 and 3, because the Note title is the page's only `<h1>`. The toolbar shows the five formats the brief asks for: Heading, Bold, List, Link, Code block. StarterKit's other harmless formats work through keyboard shortcuts.
- **The server checks every saved body.** `src/shared/schemas/note.ts` holds a written-out list of allowed node and mark names. Nodes are the blocks, such as a paragraph or heading. Marks are the inline styles, such as bold or a link. The list is copied from StarterKit's defaults in the pinned Tiptap version, checked through Context7 at build time. It is a fixed list in our code, so a Tiptap upgrade cannot quietly widen it. A small recursive function, wrapped in a zod `refine`, checks the body:
  - every node and mark type is in the list;
  - only these settings are allowed: `heading.level` (2 or 3 only), `link.href`, and `codeBlock.language` (text of 30 characters or less, or null). Any other setting on a link (for example `target` or `class`) is refused;
  - `href` must start with `https://`, `http://` or `mailto:`, so `javascript:` is refused;
  - the body is at most 512 KB of JSON and at most 20 levels deep.
- **Showing the text.** Tiptap builds the page from the checked JSON, never from raw HTML, so a Note can't inject script. When a link is shown, it gets `target="_blank"` and `rel="noopener noreferrer nofollow"`. These are never stored.
- **Plain text for search.** `noteText(doc)` is a small pure function. It joins the text of every node, with a space between blocks. Its result goes in `body_text`.
- **Saving (decision 2).**
  - The editor saves 1.5 seconds after typing stops.
  - **Only one save runs at a time.** If you type during a save, the newest text waits. It is sent when the first save returns, using the new version number. So fast typing never causes a false "changed on another device".
  - When the page is hidden (you switch apps or close the tab), the editor saves with `fetch(..., {keepalive: true})`. This only works when the request is **under 60 KB**, because browsers limit these requests to 64 KB.
  - For larger Notes, the editor relies on the 1.5-second save. While a save is still waiting, it also shows the browser's "Leave page?" warning. `shortcut: in a Note over 60 KB, closing the tab can lose up to the last 1.5 s of typing; add a localStorage draft if this happens in practice`.
  - Status text, in `aria-live="polite"`: "Saving…", "Saved 14:02", or "Couldn't save. Retrying…". A failed save retries after 2, 4 and 8 seconds, then every 30 seconds.
- **Conflicts: an exception to U7 (part of decision 2).** U7 says a conflict reloads the item and shows a toast. With autosave, a reload would throw away the text you just typed. So Notes do not follow U7.
  - When a save gets 409 `CONFLICT`, autosave stops. A banner says "This Note was changed on another device."
  - **Keep mine:** your text stays on screen. It is saved with `expectedVersion` set to the server's current version. The other version is overwritten.
  - **Load the other version:** first asks "Replace your text with the other version? Your unsaved text will be lost." If you confirm, your text is replaced with `current`.
  - Design-system §5 "Conflicts" and the decisions table get a line for this exception.
- **Deleting a Note** is a hard delete, after a confirmation. The confirmation names the Note and says how many Attachments go with it. There is no Undo, because v1 has no Undo for things the Student does by hand.

**Attachments**

- **Allowed kinds (decision 4).** Each allowed extension has a fixed content type, and the first bytes the file must start with. These live in one table in `src/server/files/rules.ts`:

  | Extension | Content type | First bytes | Opens |
  |---|---|---|---|
  | `.pdf` | `application/pdf` | `%PDF-` | in the browser (`inline`) |
  | `.docx`, `.xlsx`, `.pptx` | the Office Open XML types | `PK\x03\x04` (zip) | downloads |
  | `.doc`, `.xls`, `.ppt` | the old Office types | `D0 CF 11 E0 A1 B1 1A E1` | downloads |
  | `.png` *(if decision 4 is B)* | `image/png` | `89 50 4E 47 0D 0A 1A 0A` | in the browser |
  | `.jpg`, `.jpeg` *(if decision 4 is B)* | `image/jpeg` | `FF D8 FF` | in the browser |

  SVG, HTML and video are never allowed. Ticket 3 ships the `.pdf` row. Ticket 4 adds the rest.
- **Size:** 1 byte to 20 MB (20 × 1024 × 1024 bytes). The browser checks before uploading, and the server checks again afterwards.
- **File name:** the server removes any folder path and control characters, folds runs of spaces into one, and cuts the name to 200 characters while keeping the extension.
- **Upload in three steps:**
  1. **The browser asks for an upload.** It sends `POST /notes/:id/attachments` with the file name and size. The server checks the kind and size, writes an `uploading` row, and returns an **upload link**. The link only allows creating that one blob, and lasts 10 minutes.
  2. **The browser sends the file straight to Blob storage** with that link. It uses `XMLHttpRequest`, because `fetch` can't report upload progress. 20 MB fits in one "Put Blob" request.
  3. **The browser tells the server it has finished** (`POST /attachments/:id/complete`). The server reads the first 8 bytes with one ranged GET. The reply's `Content-Range` header (`bytes 0-7/<total>`) also gives the real size. If the size is over 20 MB, differs from what was declared, or the first bytes don't match the extension, the server **deletes the blob and the row** and replies with a field error. If the blob is missing, it replies with a field error and the row stays `uploading`. Otherwise the row becomes `ready`.
- **Half-finished uploads.** `uploading` rows are never shown or counted. Their blobs are deleted when their Note, Course or account is deleted. `shortcut: abandoned uploading rows stay hidden until their Note is deleted; add a clean-up if M3 makes them common`.
- **Opening an Attachment.** `GET /api/v1/attachments/:id/file` checks the session and ownership. Then it redirects (302) to a **read link that lasts 5 minutes**. The link sets two things:
  - the content type, from our own row;
  - `Content-Disposition`, with an ASCII fallback name plus `filename*=UTF-8''<percent-encoded name>` (RFC 5987). This makes Tamil, Sinhala and quoted names download correctly.

  A new link is made on every tap, so the short expiry never gets in the way.
- **Deleting Attachments.** The blob is deleted first. A "not found" from Blob storage counts as done. Then the row is deleted. If Blob storage fails, the row is kept and the Student sees "Couldn't delete the Attachment. Try again." So no blob is ever left without a row.
  - **An Attachment:** its blob, then its row.
  - **A Note:** the blobs of all its Attachments, in any status, then the Note.
  - **A Course** (`deleteCourse`, after the code check): the blobs of every Attachment on its Notes, then the Course. If a blob fails, the Course is kept and the dialog shows "Couldn't delete: some Attachments couldn't be erased. Try again."
  - **The account** (`deleteAccount`): after the password check and **before** the confirmation email, the blobs of every Attachment the Student has. If that fails, nothing else happens, and the Student sees "Couldn't delete your Attachments. Try again."
  - Blobs are deleted 4 at a time, so hundreds of Attachments take seconds.
- **Wording updates in completed work.** These go in ticket 3, as a linked follow-up to the completed work:
  - The account dialog (`account-section.tsx`) and the confirmation email (`templates/account-deleted.ts`) both list what gets deleted. They add "Notes and their Attachments".
  - The Course delete dialog (`course-actions.tsx`) adds "Notes and their Attachments".
  - If decision 5 keeps soft delete, the line "Backups age out within 7 days" becomes "Backups and deleted Attachments are erased within 7 days". This changes in the dialog, the email, **and CONTEXT.md** ("Security and data"). The CONTEXT.md edit is an approved-requirement change, so it is only made with your approval (decision 5).

**Search**

- **What it searches:**
  - Courses: code, name and Nicknames;
  - Assignments and Exams: titles. Deleted ones are left out. Submitted Assignments and past Exams are included;
  - Notes: title and `body_text`.
- **Which Semesters:** every Semester (decision 6, option A). Every result carries `semesterName`. It is null for the current Semester and shown for any other.
- **How it matches:**
  - The query is trimmed and must be 2–100 characters.
  - It is split into at most 5 words. Every word must appear in the item, anywhere inside a word, ignoring case.
  - `%`, `_` and `\` are escaped.
  - Part-word matching suits mixed English and Tamil or Sinhala typed in English letters. "Stemming" (matching word endings, as English full-text search does) would get these wrong.
- **How it runs:** four plain queries, **one after another** (Courses, Assignments, Exams, Notes). The database pool has only 5 connections, so the queries never run at once.
- **Order within each type:**
  - **Courses:** by code. Code, name and Nicknames all count as the "title".
  - **Assignments and Exams:** items whose title matches all the words come first, then by `created_at`, newest first.
  - **Notes:** items whose title matches all the words come first, then by `updated_at`, newest first.
  - At most 20 results per type. No paging.
- **Snippet:** for a Note, about 120 characters of `body_text` around the first match. React wraps the matched words in `<mark>` as plain text, never as HTML.
- **Where results link to.** No Assignment or Exam has its own page, and the Course page doesn't list them yet:
  - A **Course** opens `/courses/[id]`.
  - An **Assignment** whose Course and Semester are not archived opens `listHref("assignments", {status: submitted ? "submitted" : "todo", course})#assignment-<id>`.
  - An **Exam** whose Course and Semester are not archived opens `listHref("exams", {course})#exam-<id>`. Past Exams show under "Earlier".
  - An **Assignment or Exam in an archived Course or Semester** opens `/courses/[id]`. That page shows archived Courses. The search row already shows the title, the date and the status, so the Student sees the details there.
  - A **Note** opens the Note.
  - Each `DeadlineItem` row gets `id="<type>-<id>"`, so `#…` scrolls to it. This is a one-attribute change to completed #21, linked from ticket 2.

### Blob storage

- **Account (decision 3):** a new storage account just for Attachments: Standard, locally redundant (LRS), Hot tier. It has:
  - a private container `attachments`, with public access off;
  - minimum TLS 1.2;
  - blob **soft delete for 7 days** if decision 5 keeps it. Soft delete keeps a deleted blob recoverable for 7 days.

  The backup account stays as it is, so the web app's key can't touch the backups. **Creating this account is a production action.** It is done only after you approve decision 3 and ticket 3's ADR update.
- **CORS** on that account allows `PUT` from `APP_ORIGIN` only, with the headers `content-type`, `x-ms-blob-type` and `x-ms-version`. CORS is the rule that lets the browser send files to another website, here the storage account.
- **CSP:** `src/proxy.ts` builds `connect-src` as `'self' <new URL(ATTACHMENTS_BLOB_ENDPOINT).origin>`. CSP is the rule that limits which addresses the page may contact. Today `connect-src` is a fixed string. This way it allows Azure in production and Azurite in development and tests. Opening an Attachment is a normal page visit, so CSP doesn't affect it.
- **Code: `src/server/files/blob.ts`.** It calls the Blob REST API with `fetch` and no SDK, the same way the Resend client works. It has five functions:
  - `sign()`: signs a **service SAS** (a signed, time-limited link for one blob) with HMAC-SHA256 from Node's built-in `crypto`;
  - `uploadUrl()`: a link that can only create that one blob;
  - `readUrl()`: a link that can only read it, with the content type and download name set;
  - `firstBytes()`: one ranged GET for the first 8 bytes and the total size;
  - `deleteBlob()`.

  The signer adds `spr=https` (HTTPS only) when the endpoint starts with `https://`, which is always the case in production. Azurite runs over http, so the signer leaves it out there.

  There is no list call, so there is no XML to parse. The tests list blobs with the `az` CLI against Azurite to check that "no blobs are left".

  If signing proves fiddly, `@azure/storage-blob` is the fallback. The SAS format is checked against Microsoft's docs through Context7 at build time.
- **Settings** (`.env`, web container only):
  - `ATTACHMENTS_BLOB_ENDPOINT`: in production `https://<account>.blob.core.windows.net`, with Azurite `http://127.0.0.1:10000/devstoreaccount1` (the account name is in the path). `.env.example` shows both.
  - `ATTACHMENTS_ACCOUNT`

### Privacy and security

- **Private files.** Attachments are in a private container. Nobody can read one without a link signed by our server. The server only signs a link after checking the session and ownership. Read links last 5 minutes and upload links 10 minutes, each for one blob. Links are HTTPS-only in production.
- **No personal data in blob names** (`<student_id>/<uuid>`). The real file name is kept only in Postgres, and is sent to the browser through the signed link.
- **Files are served from the storage domain, not the app's domain.** So a harmful file can't run script on the app. The content type comes from our allow-list, never from the upload. SVG and HTML are never allowed.
- **The account key** is only in the web container's environment (the root-only `.env`, as in D2). If it leaked, someone could read and delete Attachments, but not backups (decision 3). This is accepted, the same as the other secrets on the VM.
- **Note text is not encrypted inside the app.** It is the Student's own writing, unlike classmates' messages. The disk and the backups are encrypted, as today.
- **Logs** hold ids and sizes only. Note text and file names are never logged.
- **Deleting a Course or the account erases its Attachments** in the same release that adds them (ticket 3).
- **Tiptap packages** are covered by `npm audit` and pinned to exact versions.

### Performance, memory and cost

- **Web memory:** unchanged. Files never pass through Node. Note bodies are at most 512 KB. Signing a link is one HMAC.
- **Database:** tiny (hundreds of Notes). Search is a plain `ILIKE` scan with **no index**. With hundreds of rows it takes milliseconds. Code comment: `shortcut: no search index; add a pg_trgm GIN index if notes grow past ~50k rows`.
- **Browser:** Tiptap loads only on the Note page. Its size is checked on your phone.
- **Storage limit:** none in M2. One Student adding lecture PDFs by hand won't reach the cost that would matter. M3 decides on a limit, when files are saved automatically. `shortcut: no storage limit; add one in M3`.

That 5 GB is shared by the whole subscription, so it includes the backups. Soft-deleted blobs are billed for 7 days. Above 5 GB, storage costs about $0.02 per GB per month: a few cents. The first 100 GB a month of downloads is free. Requests cost cents. This goes in ADR-0001's priced list.

### Domain rules

**Dark mode**

- **Each color token is written once** in `src/app/globals.css` with CSS `light-dark()`, for example `--background: light-dark(#F8FAFC, #0B1120)`. `:root` gets `color-scheme: light dark`. The browser then picks the right value, and its own date and time pickers and scroll bars turn dark too. All current browsers support `light-dark()` (Chrome and Android Chrome 123+, Safari 17.5+, Firefox 120+). The current `[data-theme="dark"]` block is removed, because its values move into the `light-dark()` pairs.
- **shadcn's `dark:` classes** (in `input`, `button`, `select`, `badge`, `checkbox`, `textarea`) need the `dark` variant to match. Today it is `@custom-variant dark (&:is([data-theme="dark"] *))`, which nothing ever sets. It becomes `@custom-variant dark (@media (prefers-color-scheme: dark))`.

**Calendar Feed**

- **The token** is 32 random bytes from `crypto.randomBytes`, written in base64url (43 characters, 256 bits). It can't be guessed. Only its SHA-256 hash is stored (decision 4). The full link is shown once, when it is created or reset.
- **The link** is `${APP_ORIGIN}/api/feed/<token>.ics`. It is HTTPS only (Caddy and HSTS). The `.ics` ending helps some calendar apps. The route strips it, and also accepts the link without it.
- **Two written exceptions to house rules:**
  1. The route is `/api/feed/…`, not `/api/v1/…` (D3). Like `/api/health`, it is unversioned, because a subscribed link has to keep working forever.
  2. `findStudentByFeedToken(tokenHash)` in `src/server/data/calendar-feed.ts` is the only data function that doesn't take `studentId` first (design §6). The token is the key. A comment in the code says so. Everything it loads after that is scoped by the `studentId` it finds.
- **What it contains** (one event for each Occurrence, so Session Changes are applied without any repeat rules):
  - **Classes:** every Occurrence from `getOccurrences(studentId, today − 56 days, today + 182 days)`, so 8 weeks back to 26 weeks ahead. That range is cut to Semester dates anyway, and Archived Courses and Semesters are already left out. Course codes come from `listCourseOptions()`.
    - Title: `CS2010 Lecture`. A moved class gets ` (moved)`, an extra class gets ` (extra)`. The class's location goes in the event's location.
    - **Cancelled Occurrences are left out**, so the calendar app removes them on its next refresh.
    - **The event id (UID) stays the same when a class moves:** `occ-<classSessionId>-<original date>@course-manager`, or `extra-<sessionChangeId>@course-manager` for an extra class. So the calendar app moves the event instead of showing two.
  - **Deadlines:** `loadOpenDeadlines(studentId, { examsFrom: today − 56 days, includeTba: false })`. So Exams older than 8 weeks drop out, the same as classes. Overdue Assignments that are still open stay in, because they are still Deadlines. A Submitted Assignment drops out, because it is no longer a Deadline (GLOSSARY). TBA Exams are left out, because they have no date.
    - Assignment: `Due: CS2010 Lab 4 report`, a 30-minute event that ends at the due time. With no announced time it runs 23:29–23:59, and the title ends with ` (time not announced)`.
    - Exam: `Exam: CS2010 Mid-term`, 1 hour from its start time, or a whole-day event when it has a date but no time.
    - Event ids: `assignment-<id>@course-manager` and `exam-<id>@course-manager`.
  - **Every event** has `DTSTAMP` (the time the feed was built, in UTC, as the calendar file standard RFC 5545 requires) and `SEQUENCE`. For Assignments and Exams, `SEQUENCE` is the item's `version`. For classes it is `sessionChangeVersion`, or 0 for a normal class. This helps calendar apps that keep an old copy notice that an event changed.
  - **Left out on purpose:** descriptions, topics, where to submit, message text and sender names. Each event gets only a link back to the app (`/calendar?day=YYYY-MM-DD`). There are no calendar alarms: email is the reminder (Alternative I), and Google ignores alarms in subscribed calendars anyway.
- **Times** are written in UTC (`…Z`). Asia/Colombo has no daylight saving, so no time-zone block is needed. Whole-day events use plain dates.
- **The file** is written by a small pure function, `src/server/domain/ics.ts`, with no library. It uses CRLF line endings, escapes `\ ; ,` and newlines, and folds lines at 75 bytes without splitting a UTF-8 character. The header lines are `VERSION:2.0`, `PRODID:-//Course-manager//EN`, `METHOD:PUBLISH`, `X-WR-CALNAME:Course-manager`, plus the refresh hints `REFRESH-INTERVAL;VALUE=DURATION:PT1H` and `X-PUBLISHED-TTL:PT1H`. Apple and Outlook follow these hints. Google does not.
- **Timing:** each fetch builds the feed fresh. Google Calendar decides on its own how often to fetch, often only every 12 to 24 hours. The Settings text says so. The Daily Digest and Final Reminder stay the reminders.
- **No rate limit.** A wrong token costs one lookup on a unique index, and calendar apps such as Google fetch from many different IP addresses. If load ever becomes a real problem, a limit can be added then.

**Export my data** (assuming decision 5 is "what you made or can see")

- **File:** `course-manager-export-YYYY-MM-DD.json`. The date is today's date in Asia/Colombo, not UTC.
- **Shape:** `{ formatVersion: 1, exportedAt, timeZone: "Asia/Colombo", student: { email, name, createdAt }, tables: { <table name>: [rows] } }`. Rows use the database's column names.
- **Exported tables:** `semester`, `course`, `course_nickname`, `class_session`, `session_change`, `assignment`, `exam`, `wa_group` (the group names and what each is linked to), `auto_change` (the Activity Log's change items, with their summaries and before and after values) and `activity_event` (the Activity Log's event items). Tables from other M2 groups (Attendance, Notes, Attachment details, Session Groups, Break Weeks and Holidays) join this list when they land.
- **Not exported:**
  - Secrets: `account` (password hashes), `session`, `verification`, `rate_limit`, `wa_session` and `wa_auth_key` (these give full access to your WhatsApp), and `calendar_feed_token`.
  - Internal records: `inbox_message`, `auto_change_source`, `ai_batch`, `entity_version`, `suppression`, `email_log` and `unknown_course_mention`.
  - Because no message rows are exported, no classmate's message text or name (`text_enc`, `sender_name`, `decision_reason`, `pending_ops`) can be in the file. So D1's promise (message text is erased when its Semester is archived) also holds for exports.
- **Not per Student:** `health_signal` and `user` itself (the `student` block takes only email, name and created date from it).
- **The guard test** goes through **every** table in `schema.ts`, not only those with a `student_id` column. Each table must be on exactly one of three lists: exported, not exported, or not per Student. So a new table from another group (including a link table with no `student_id`, like `auto_change_source`) can't be silently left out or leaked.
- **How it is built:** `src/server/data/export.ts` runs one query per exported table, each `where student_id = $1`, all inside one `READ ONLY, REPEATABLE READ` transaction. This means the file is one consistent snapshot, even if the worker writes during the export. It uses 1 of the pool's 5 connections for well under a second. The result is sent as one JSON response with `Content-Disposition: attachment`.
- **Size:** after several years, mostly `auto_change` rows, a few MB. That is small for the 256 MB `web` container and the 192 MB Postgres. The code carries the comment `shortcut: the whole export is built in memory; move to paged streaming if exports pass about 20 MB.`

### Privacy and security

- **The feed token is in the URL.** That is how calendar subscriptions work, so it is handled like a password:
  - 256 random bits, and only its hash is stored. A database backup alone can't give the link back.
  - Caddy keeps no access log. The feed route never logs its path or token. Its error log says only "feed request failed".
  - Unknown, reset and turned-off tokens all get the same empty 404.
  - The feed is read-only and holds the minimum: Course codes, class kinds, locations and Deadline titles. No message text, no names, no descriptions.
  - Reset and Turn off stop the old link at once. "Last fetched" helps you see whether a calendar app is using it.
- **Third party:** subscribing puts that minimum on Google's (or another calendar app's) servers. Settings says this before the link is made.
- **Export:**
  - It needs a signed-in session. Every query is scoped by `student_id`, like every other read.
  - Secrets and message rows are never exported. The guard test makes sure every table is classified.
  - The file on your device is not encrypted. The text next to the button says so.
- **Account deletion:** `calendar_feed_token` cascades with the user row, so the link returns 404 straight away. An export you already downloaded is your own copy. Deleting Attachment files from Blob storage belongs to the Notes and files group.
- **The theme cookie** (only with the switch) holds only `light` or `dark`. It is not a secret.

### Performance and memory

- No new container, no new package, no worker change. The 750 MB budget is unchanged.
- **Feed:** one `getOccurrences()` call and one `loadOpenDeadlines()` call. About 300 to 500 events for a Semester, under 150 KB of text. It is built fresh on each fetch, and a calendar app fetches a few times a day.
- **Export:** a few small queries in one read-only transaction. A few MB even after several years (see the `shortcut:` note above).
- **Dark mode:** CSS only. With the switch, the root layout reads one cookie.
- **Sign-in:** one extra server redirect (`/setup` to `/`) when setup is done. It costs one read of the user row.
